## 読者が知るべきこと

日報を一冊読めば、その日までに各社が何を提供し、どう稼ぎ、どこで競争し、何が変化し、どの制約に直面しているかを説明できること。Static は各社の事業を初めて調べる読者にも通じる継続的な企業資料とする。仮説・予測・次回測定は事実を読んだ後の判断を助けるもので、会社情報の代わりにはしない。

企業5冊と市場・シナリオの2冊を、製品・顧客・提供条件・資金・販路・経緯・制約を含む本文へ改稿しました。xAIのSpaceXによる買収、Seed2.1／Seedance2.5の発表も補い、古い記事の再取得を新発表としていた扱いを修正しました。直近7日の日報には会社ごとの状態、市場・雇用、期間別判断を本文内に収録し、再調査による補足と当時の収集記録を区別しました。復元に使った共通本文と日付別の追加資料は`data/report_reconstruction/2026-09-22/`に残しています。

継続生成は7冊の基礎本文を読み、検証した`dossier_section`だけを追記台帳で更新します。日報とStaticは同じ確定スナップショットから生成します。新着なし・partialでは情報を維持し、failedでも既存日報がない場合は以前の状態を「参考資料」と明示して残します。failedの参考資料は通常の成功扱いで自動公開しません。再開時にモデルや後日変更された基礎本文へ依存しないよう、採用した全文も保存します。

- 未来の確認、出典の欠落、別会社への履歴参照、同じ節の履歴分岐、未知の節、未検証の新しい引用URLを拒否。

## 実モデル接続で判明した入力欠落

GitHub Actionsの実行確認で、模擬モデルだけでは検出できない二つの不備が見つかりました。進行説明と最終回答を連結してJSONとして解析していたため、最終回答だけを検証するよう修正しました。さらに、文脈JSONを1行で添付したため、OpenCode 1.18.31のReadによる1行2,000文字の切り詰めが発生していました。収集担当には資料の後半や段階別の指示が届いていませんでした。

ローカルの同じCLIと、実キーを使わない模擬HTTP提供元で入力経路を検証しました。標準入力へ渡す方式では5万文字と末尾の印がモデル要求に残ることを確認しています。段階の指示も直接渡し、文脈JSONは標準入力で送信します。添付経由の切り詰めとOSのコマンド引数長への依存を避けます。自動生成タイトルのための余分な呼出しも行いません。

自動テストには最終回答が不正な場合に古いJSONへ戻らないこと、長い入力の全文を送信することを含みます。失敗時は開発者が定義した検証理由と数値の使用量を残し、応答本文や認証情報はログへ出しません。

実モデルが記録の分類値を推測しないよう、13種類のSchemaを実行時の許容値と一致させて渡します。資料を大量に読むと自動要約後に最終回答の形式が崩れたため、自動compactionを無効にしました。収集には概要・節名・出典の索引を渡し、原資料5件・検索2回までに限定します。分析・反証・裁定・日報・Staticは全本文を使います。時間やモデルの上限に達した実行を成功へ読み替えません。

原資料の再取得で個別のHTTPエラーが発生した場合は、その資料と依存する記録を除外し、取得済み資料を欠測付きのpartialとして保存します。部分収集では新しい判断を生成せず、既存の会社情報を維持します。この処理と、契約違反を欠測へ隠さないことも検証しています。
